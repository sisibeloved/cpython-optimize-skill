# 指令调度

来源：Cooper & Torczon《Engineering a Compiler》2nd ed，Ch12：
§12.1 Introduction（PDF p664）、§12.2 The Instruction-Scheduling Problem（p668）、
§12.3 Local List Scheduling（p676）、§12.4 Regional Scheduling（p686）、
§12.5 Advanced Topics（p691，含 software pipelining）。
页码为 PDF 页，印刷页 ≈ PDF−25。

## 问题定义

重排指令顺序以提高 ILP（指令级并行），**不改变数据与控制依赖下的可观测行为**。
目标机器的三个属性决定一切：
- 功能单元数量与流水线结构（一个周期发射几条）
- 操作延迟（结果几周期可用）
- 依赖检查是硬件做（乱序机器，如大核 x86）还是编译器做（顺序发射，如多数 ARM 小核/传统模式）

A64 上：顺序核（Cortex-A55 类）调度收益大；乱序核硬件会兜底，编译器调度的
边际收益小——这是 Kunpeng 与 x86 大核对比时"同一 IR 不同收益"的常见根因之一
（微架构结论需 perf 证据，见 `cinderx-isa-microarch-compare`，本文件只给框架）。

## 依赖类型

| 依赖 | 含义 | 消除手段 |
|---|---|---|
| RAW（真依赖） | 写后读 | 不可消除，只能隔开延迟 |
| WAR | 读后写 | 寄存器重命名消除 |
| WAW | 写后写 | 寄存器重命名消除 |
| 控制依赖 | 分支下才执行 | if-conversion（条件执行/条件选择指令）、分支预测 |

A64 的 CSEL/CSINC 族正是控制依赖转数据依赖的硬件支持——
"用条件选择取代比较+分支"的检索路径见 `isa-instruction-lookup` 的意图映射表。

## 经典算法

- **表调度（list scheduling，§12.3）**：自 1970s 末以来的主导范式，是"方法框架"
  而非单一算法。四步（§12.3.1，p651 印刷页）：
  ①重命名消除反依赖（可选但推荐）→ ②自底向上建依赖图 D（边标注延迟）→
  ③给操作算优先级 → ④逐周期从就绪集按优先级发射。
  前向（早发射）与反向（从块尾回推，常对延迟更好）两种变体（§12.3.2/12.3.3）。
- 优先启发式：关键路径优先、依赖数优先、延迟优先的组合。
- **区域调度（§12.4）**：trace scheduling 等把 list scheduling 应用到跨块长序列——
  本质是"创造条件让 list scheduling 跑在更长直线码上"。
- **软件流水（§12.5 Advanced，p691）**：modulo scheduling 让不同迭代的代码交错
  执行，饱和流水线；循环展开（unrolling）是它的低成本替代。
- 跨块搬指令的正确性约束复杂（把操作搬上原本不存在它的路径 / 从必要路径移走），
  JIT 通常不做或极保守（§12.3 开篇明确列出这两类风险）。

## 调度与寄存器分配的相互制约

- 调度拉长寄存器活跃区间 → 分配压力上升 → spill 增多 → 反而更慢。
- 先分配后调度：load 早提会造成占用；先调度后分配：move 插入破坏调度。
- 生产编译器多迭代或一体化处理；分析"某次 spill 风暴"时先看是不是调度造成
  的活跃区间拉长（对照 `register-allocation.md`）。

## 读机器码时的判读框架

1. 找块内关键路径（RAW 链最长者），看发射间隙是否喂饱流水线。
2. load-use 间隔是否 ≥ load 延迟（不满足且是顺序核 → 停顿）。
3. 分支密集块：可否 if-conversion / 合并条件（CCMP）。
4. 循环体：迭代间 RAW 链是否可软件流水/unroll 打断（JIT 受编译预算约束常保守）。

## 落地查证

- 判读框架第 2 条的 load 延迟、第 3 条的条件选择/条件比较指令 → `lookup_instruction`
  取规格；A64 侧 CSEL/CCMP 族、x86 侧 CMOVcc/SETcc 须查库确认（意图映射表有族对照）。
- 微架构延迟/吞吐数字不在 ISA 库（走 perf/TRM），本文档只提供判读顺序，不给数字。
